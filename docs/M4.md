# M4 — Transfer Calculator

## Product goal

Answer one question:

> **If this player moves to another league, what might happen to his attacking output?**

Not: "Is this player good?" Not: "Should the club buy him?" And definitely not: "Will he succeed?"

The model predicts **output retention**, not career success.

---

# 1. Core User Journey

```text
Choose player → Choose origin → Choose destination → Optional destination club → Run prediction
→ Expected output → Expected retention → Probability of retaining ≥75% → Prediction range
→ Why? → What could make this wrong? → Share
```

The entire experience should feel like opening a **recruitment brief**.

---

# 2. Route

`/football/tools/transfer`

Shareable state: `/football/tools/transfer?player=...&from=premier-league&to=serie-a&club=...`

---

# 3. Hero

**Will his game travel?**

Subheading:

> Estimate how much of a player's attacking output may survive a move between European leagues.

Then a methodological qualifier:

> The model predicts post-transfer attacking output using player history, league context and transfer characteristics. It does not predict overall player quality or career success.

This disclaimer should be visible **before** someone runs the model.

---

# 4. Input Experience

Desktop:

```text
PLAYER            [ Search player...            ]
FROM              [ Premier League ▼ ]
TO                [ Serie A ▼ ]
DESTINATION CLUB  [ Optional — select club ▼ ]
                  [ Run prediction ]
```

The club field should be explicitly **Optional** because the research says destination club strength matters, but we shouldn't imply that the model predicts every club-specific factor.

---

# 5. Player Selection

Reuse M3's `PlayerSearch`. Result: "Bruno Fernandes · Manchester United · Premier League". Then show: "Available history: 3 seasons".

If the model requires a minimum history and the player doesn't qualify: **Insufficient history**. Explain exactly why. No prediction should be generated from an invalid sample.

---

# 6. Origin League

In most cases we can infer this from the player's current/selected history. But still display it ("PLAYER Bruno Fernandes · ORIGIN Premier League"). Don't make users select something that can be safely inferred unless there is a legitimate reason.

---

# 7. Destination League

This is the primary decision variable. Dropdown: Premier League · La Liga · Serie A · Bundesliga · Ligue 1. Potentially other supported leagues if the underlying Study 5 model supports them.

**The UI must derive this from the model's supported destinations.** Don't hardcode extra leagues just because they exist in football.

---

# 8. Destination Club

This is optional. Flow: "DESTINATION CLUB [ Any club ▼ ]". Then:

> Club strength can influence expected retention. Leaving this blank produces a league-level estimate.

This is excellent because it teaches the user something about the model.

---

# 9. Run State

After clicking **Run prediction**:

```text
ANALYSING PLAYER HISTORY
✓ Player history
✓ League context
✓ Transfer context
→ Generating prediction
```

This should take very little time if the model is precomputed/API-backed. Don't fake a 5-second loading animation.

The result should immediately feel like a scouting report.

```text
TRANSFER PROJECTION
BRUNO FERNANDES
Premier League → Serie A

Expected attacking output
0.XX xG+xA / 90

```

These are the two numbers that matter most.

# 11. Retention Visualization

```text
PRE-TRANSFER            0.XX  ████████████████████
POST-TRANSFER EXPECTED  0.XX  ████████████████
```

Then: **Expected retention: 96%**. Avoid gauges/speedometers. They look like car dashboards and imply more precision than the model deserves.

---

# 12. Probability Threshold

Study 5 gives us: probability of retaining ≥75% of output. Label it clearly:

> **Probability of retaining at least 75% of pre-transfer attacking output**

Not: "80% chance of success." Huge difference.

---

# 13. Prediction Range

This is one of the most important parts of the tool.

```text
80% PREDICTION RANGE
0.31 ───────── 0.51
              ▲
            0.41
```

Then: "Typical prediction range is approximately ±0.2 xG+xA/90." This communicates uncertainty visually. Don't hide uncertainty in a tooltip.

---

# 14. Confidence vs Prediction Range

Be precise with language. Don't call the ±0.2 range a confidence interval unless that's exactly what the underlying model produces. Use the research's terminology: **80% prediction range**. Then separately: "Model performance on locked test data: R² = .76."

---

# 15. Why This Prediction?

The equivalent of M3's "Why does this player look similar?". Here: **Why does the model expect this outcome?**

Potential drivers: Player history · League difficulty · Age · Destination club strength · Recent performance jump.

Important constraint: **Only show drivers that the final model actually supports.** Study 5 found: age matters · destination club strength matters · recent performance jump predicts larger drop · league effect matters · role doesn't add predictive value after regression-to-mean · three-season consistency doesn't add predictive value · profile distinctiveness doesn't add predictive value · penalty duties don't add predictive value · loans don't add predictive value.

So don't build a generic "AI explanation" box. It must reflect the actual model.

---

# 16. Model Evolution

**How much does context improve the prediction?**

```text
                 MAE       R²
Naive            .129      .58
Role average     .117      .65
Context          .102      .74
Final model      .096      .76
```

Then: "Each step adds information while the final model is evaluated only once on unseen transfers."

---

# 17. Locked Test

Compact research integrity card: "MODEL VALIDATION · 142 unseen transfers · Test period: 2023/24 — 2025/26 · Model locked before testing." Then: "This prediction model was fixed before the test seasons and evaluated once on 142 unseen moves." This should be one of the strongest trust signals on the page.

# 19. The Ugarte Problem

**Where the model can fail**

> The model is built primarily around attacking output. It cannot see defensive actions, completed passes, carries or possession.

```text
Ugarte · Predicted 0.02 · Actual 0.14
```

> Ugarte is a useful example of why model output should not be interpreted as a complete player evaluation.

This is **gold for credibility**. Don't bury it.

# 21. "What This Doesn't Tell You"

The model does not predict: injuries · adaptation outside attacking output · defensive contribution · possession/carrying contribution · transfer fee · contract · team tactics · fixture congestion · cup competition · overall player value. The broader dataset limitations should be accessible.

# 28. Critical Product Rule

> **Never turn the transfer model into a single "Transfer Score."**

There is no validated 0–100 score in the research. A score like **Transferability: 82/100** would look fantastic. It would also be scientifically dishonest. The actual product should show: expected output · expected retention · probability threshold · prediction range · drivers · uncertainty.
