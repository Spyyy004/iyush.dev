# 1. M1 Product Objective

The website should immediately communicate:

> **This isn't a football blog. It's a football research product.**

Within the first 10 seconds, a visitor should understand:

1. What is being investigated?
2. Who built it?
3. How much data is behind it?
4. What are the five studies?
5. Why should I explore further?

The emotional target:

**Curious → intrigued → impressed → wants to investigate**

Not:

**“Nice portfolio website.”**

# 2. Visual Identity

We're extending `iyush.dev`, but `/football` gets its own identity.

### Design language

**Football research lab × editorial publication × developer tool**

Think:

- Financial Times editorial hierarchy
- scientific paper precision
- modern developer tooling
- football analytics interface

But **not**:

- ESPN
- Transfermarkt
- FIFA Ultimate Team
- betting website
- SaaS dashboard
- generic dark-mode portfolio

# 3. Colour System

Keep the palette extremely restrained.

### Base

```text
Background        #0B0B0B
Surface           #111111
Surface Elevated  #171717
Border            #242424

Primary Text      #F2F0EA
Secondary Text    #A3A3A3
Muted Text        #666666
```

### Accent

Use a **muted football-red**:

```text
Accent             #B83A3A
Accent Hover       #D04A4A
Accent Subtle      rgba(184,58,58,0.12)
```

The important rule:

> **Red is semantic, not decoration.**

Use it for:

- active navigation
- important findings
- selected states
- chart emphasis
- links/CTAs
- warnings/limitations

Don't make the entire website red.

### Positive / negative

Don't rely purely on green/red.

Use:

```text
Positive → restrained green
Negative → restrained red
Neutral  → grey
```

But always pair colour with:

- `+27%`
- `−14%`
- `No reliable effect`
- icons/text

This makes the UI accessible.

# 4. Typography

I want two typographic personalities.

## Display / editorial

Use something like:

**DM Serif Display**  
or  
**Instrument Serif**

Fallback:

```text
Georgia, serif
```

Large research headlines should feel editorial rather than like a SaaS landing page.

Example:

> **What actually belongs to the player?**

## UI / body

Use:

**Inter**

Fallback:

```text
system-ui, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif
```

## Data / technical

Use:

**JetBrains Mono**

Fallback:

```text
ui-monospace, SFMono-Regular, Menlo, monospace
```

Use monospace for:

- dataset counts
- model names
- statistical values
- URLs
- study numbers
- technical labels

# 6. Layout System

Use a 12-column desktop grid.

### Desktop

```text
Max width: 1280px
Horizontal padding: 32px
Grid: 12 columns
Gap: 20–24px
```

### Tablet

```text
Max width: 1024px
Padding: 24px
Grid: 8 columns
```

### Mobile

```text
Padding: 20px
Grid: 4 columns
```

Suggested breakpoints:

```text
Mobile       < 640px
Tablet       640–1023px
Desktop      1024–1279px
Wide         ≥ 1280px
```

Avoid designing around device-specific breakpoints.


# 12. The Five-Study Journey

This is **not five cards in a row.**

It should feel like an investigation unfolding.

Desktop:

```text
01 ─ Environment
       Does weather change performance?
       Mostly no.

02 ─ Home Advantage
       Does playing at home change output?
       Yes. But not because some players
       are simply "home specialists."

03 ─ Opposition
       Do some players thrive against elite teams?
       We couldn't find reliable evidence.

04 ─ Similarity
       Can we find players who play alike?
       Yes — within limits.

05 ─ Transferability
       Does similarity predict what happens
       after a move?
       No. Player history does better.
```

Visual structure:

A vertical line on the left.

Each study occupies a large horizontal row.

Example:

```text
01
│
├── ENVIRONMENT
│   Weather changes surprisingly little.
│
│   [ finding / chart ]
│
02
│
├── HOME ADVANTAGE
│   Everyone gets better at home.
│
│   [ finding / chart ]
```

This creates narrative momentum.

# 14. Major Findings

After the journey:

# **Four things the data changed my mind about.**

This is stronger than simply saying "Key Findings."

Four findings:

### 01
**Everyone gets better at home.**

`+27% xG`

But:

> No reliable individual home specialists.

### 02
**There may be no such thing as a "big-game player" — at least in this data.**

`0 / 23,022`

No reliable player × metric estimates.

### 03
**Bruno Fernandes doesn't have a statistical twin in Serie A.**

`3.6 SD`

Bruno's chance creation vs Serie A's best comparable profile at `1.9 SD`.

### 04
**Similarity doesn't predict transfer performance.**

`+0.000`

Adding Study 4 similarity changed Study 5's prediction error by essentially nothing.

This section is potentially the most shareable section on the homepage.

# 22. Chart Design

Charts should feel like **research figures**, not BI dashboards.

Rules:

### Default

- no unnecessary gridlines
- minimal axes
- direct labels where possible
- annotation > legend
- muted colours
- one highlighted series
- source/method note below

Example:

```text
HOME xG

+30% ┤                    ●
     │                 ╱
+20% ┤             ●──╯
     │          ╱
+10% ┤      ●──╯
     │
  0% ┼────────────────────
        Closed     Open
```

Every chart should have:

**What you're looking at**

and optionally:

**Why it matters**

Don't make users reverse-engineer charts.

---

# 23. Chart States

Every chart component must support:

### Loading

Simple skeleton.

### Loaded

Actual chart.

### Empty

```text
No result for this combination.
Try another player or season.
```

### Error

```text
Something went wrong loading this result.

Try again →
```

### Insufficient sample

Important for research:

```text
Insufficient data

This comparison doesn't meet the minimum
sample required by the model.
```

Never silently display weak analysis.

---

# 24. Interaction Design

Motion should communicate **state**, not decoration.

Allowed:

- chart transitions
- accordion expansion
- search result transitions
- hover states
- page transitions
- selected study state

Avoid:

- floating footballs
- particles
- cursor trails
- spinning charts
- parallax everywhere
- giant entrance animations

### Motion duration

```text
Micro: 120–180ms
Normal: 200–300ms
Large: 300–450ms
```

Respect:

```text
prefers-reduced-motion
```

---

# 28. Accessibility

Non-negotiable.

### Requirements

- semantic HTML
- keyboard navigation
- visible focus
- WCAG AA contrast
- 44px minimum interactive target
- charts have text summaries
- colour isn't the sole information carrier
- reduced-motion support
- proper heading hierarchy
- form labels
- accessible tooltips
- screen-reader labels for icons

---

# 29. Performance

The homepage should feel instant.

Rules:

### Do

- server/render static research content where possible
- lazy-load charts
- lazy-load heavy interactive tools
- precompute research results
- send only required data
- optimize fonts
- use responsive images if images are eventually introduced

### Don't

- ship the entire player dataset
- run statistical models in the browser
- load every chart on initial page load
- add dependencies for tiny UI effects

Target:

> **The visitor should see meaningful content before the analytics machinery loads.**

# 31. M1 Data Boundary

The design system must **not** assume that the frontend calculates research.

Architecture remains:

```text
RAW DATA
   ↓
RESEARCH PIPELINE
   ↓
STATISTICAL MODELS
   ↓
VALIDATED OUTPUTS
   ↓
FRONTEND DATA
   ↓
UI
```

The frontend receives things like:

```typescript
{
  metric: "xG",
  value: 0.27,
  unit: "relative_change",
  confidenceInterval: [...],
  sampleSize: ...
}
```

It should **not** receive raw matches and calculate the result.

# 32. Homepage Acceptance Criteria

M1 homepage design is approved only if:

### Narrative

- [ ] Visitor understands the core question immediately
- [ ] Five studies read as one investigation
- [ ] Research is the protagonist
- [ ] Context → player signal → transferability is clear

### Visual

- [ ] Feels like research/editorial/developer hybrid
- [ ] Doesn't look like a generic football dashboard
- [ ] Doesn't look like a betting product
- [ ] Doesn't rely on football imagery
- [ ] Typography hierarchy feels intentional
- [ ] Red accent is restrained

### UX

- [ ] Every major finding has context
- [ ] Jargon has glossary support
- [ ] Charts explain themselves
- [ ] Tools have obvious entry points
- [ ] Shareability is built into the architecture

### Technical

- [ ] Responsive behaviour defined
- [ ] Accessibility states defined
- [ ] Loading/empty/error states defined
- [ ] Research/frontend boundary defined
- [ ] No unnecessary dependencies
