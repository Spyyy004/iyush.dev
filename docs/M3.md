# M3 — Similarity Explorer

This should be our next milestone.

The reason I'm putting it before the Transfer Calculator is deliberate:

**Study 4 is the most intuitive interactive experience.**

A football fan immediately understands:

> “Show me players who play like Bruno.”

A recruiter understands:

> “Find me alternatives for this player.”

An analyst understands:

> “Show me how the similarity model actually works.”

And technically, it gives us the first real test of our **frontend ↔ precomputed research output architecture**.

---

# M3 Product Goal

Build:

> **A player similarity research tool that lets users discover statistically similar players and understand why they match — and where they don't.**

The core principle:

> **Similarity is descriptive, not predictive.**

The tool should never imply:

> "This player is 87% as good as Bruno."

Instead:

> "This player's adjusted attacking profile is structurally similar to Bruno's."

And then:

> **Here's where the similarity comes from.**

# 4. Input Validation

- **No player:** "Select a player to continue."
- **Player insufficient data:** "Not enough data — This player does not meet the minimum profile requirements for this comparison."
- **No destination league:** obvious.
- **No results:** "No comparable profiles found. Try: • a different league • a longer profile window • another player"

---

# 5. Profile Window

Options: 1 season · 2 seasons · 3 seasons. Default: **3 seasons**.

Why? The Study 4 methodology uses three-season profiles to improve robustness. Don't expose that as a random UI preference. Explain:

> Longer profiles reduce the influence of short-term variation.

# 8. Why This Player?

This is arguably the most important feature. Clicking a result should reveal: **Why does Samardžić look similar?** Then break the profile into dimensions:

```text
SIMILARITY DRIVERS

Chance creation        Strong match
Shot volume             Strong match
xG/shot                 Moderate match
In-box share            Moderate match
xGBuildup               Strong match
Headed share            Weak match
```

Use language like **Strong match / Moderate match / Divergence** rather than fake numerical certainty.

# 11. The "Breaks Down Here" Section

Every comparison must contain **Where the similarity breaks down**.

> Samardžić resembles Bruno in chance creation and involvement, but diverges more strongly in headed involvement and shooting profile.

```text
BIGGEST DIFFERENCES

Headed share       █████████████
xG / shot          ███████
In-box share       █████
```

This prevents confirmation bias. The user shouldn't only see why the model likes a player.


And then: "None matches Bruno's chance creation profile at the same level."

---

# 13. The Important Disclaimer

Under results:

> **Similarity ≠ predicted performance.**
>
> This model describes how similar two attacking profiles are. It does not estimate how well the player would perform after changing leagues or clubs.

Then: **Want to estimate that? → Try the Transfer Calculator.** This is the bridge into M4.

---

# 14. Destination League

The model adjusts profiles for league context. "Bruno Fernandes + Serie A" means: *Which players have profiles resembling Bruno in the context of Serie A?*

Tooltip — **Why destination league matters:**

> Player output varies with league context. The similarity model adjusts for league differences before comparing profiles.

---

# 15. Role

Study 4 uses seven data-derived roles. The UI should **not make users understand those roles upfront.** Display e.g. "ROLE · Attacking midfielder", or if the model assigns roles automatically, **Role: model-assigned**, with tooltip:

> The model groups players into seven data-derived attacking roles based on their statistical profiles.

Don't make the fan choose "Role 4."

---

# 16. Seven Roles

If exposed anywhere, give them human-readable labels — but **don't invent labels now.** Unless the underlying research artifact specifies the exact role definitions/names, M3 should retrieve them from the actual model output rather than inventing UI labels. This is one of those areas where the coding agent should **stop rather than guess.**

---

# 17. Result Ranking

The ranked list should include: Rank · Player · Current club · League · Role · Similarity. Optional: Why matched.

Don't include: transfer value, age, salary, contract, market value. Those aren't part of this research model. We shouldn't gradually turn the tool into Transfermarkt.

---

# 18. Filters

Keep MVP filters very limited. **Required:** destination league, profile window. **Potential later:** age, role, minutes, league, position — but **do not build these in M3 unless the underlying research supports them.**

---

# 19. Compare Mode

Click **Compare** → "Bruno Fernandes VS Lazar Samardžić". Persistent header: "← Back to results · BRUNO FERNANDES vs LAZAR SAMARDŽIĆ". Main content: Profile · Similarity drivers · Biggest differences · Context · Interpretation.

---

# 20. Interpretation

Every comparison needs a human-readable conclusion.

> **Bottom line**
>
> Samardžić is one of the closer statistical profiles to Bruno in the selected population, particularly in chance creation and attacking involvement. But the profiles diverge meaningfully in other dimensions, so this should be treated as a similarity lead rather than a like-for-like replacement.

The model gives numbers. **The product gives meaning.**

# 24. "What the Model Doesn't Know"

**The model sees:** attacking output, chance creation, shooting profile, involvement, profile shape.  
**The model does not see:** defensive actions, completed passes, carries, possession, injuries, transfer fees, contracts.

This limitation already exists in the research dataset. It should be surfaced directly in the tool.

---

# 25. Confidence Language

Don't use "92% confidence that Player X is Bruno's replacement." Use **Strong profile match** or **Moderate profile match**, and explain the underlying similarity methodology.

---

# 26. Empty / Loading States

- **Initial:** "Find a player to begin. The model compares adjusted attacking profiles across European leagues."
- **Searching:** "Finding player..."
- **Calculating:** "Comparing profile... 9 dimensions · Context adjusted · Role normalized" (a three-step loading state that explains what the model is doing).
- **Error:** "We couldn't calculate this comparison. Try again." No technical stack trace.

# 28. Data Architecture

M3 is where we prove the precomputed architecture.

```typescript
type SimilarityQuery = {
  playerId: string
  destinationLeague: string
  seasons: 1 | 2 | 3
}

type SimilarityResult = {
  player: PlayerProfile
  destinationLeague: League
  profileWindow: number
  results: SimilarPlayer[]
  methodology: {
    metrics: string[]
    adjustment: string
    roleNormalization: string
  }
}

type SimilarPlayer = {
  player: PlayerProfile
  similarity: number
  drivers: SimilarityDimension[]
  divergences: SimilarityDimension[]
}
```

**Exact fields should be adapted to the actual existing Study 4 outputs.** Do not make the coding agent manufacture a new similarity calculation in JavaScript.

---

# 29. Performance

Target: **<500ms perceived response after cached/precomputed data loads.** The actual model should never run in the browser.

Ideal: `User query → API / static JSON lookup → Precomputed result → UI`.  
Not: `Browser → 525k player matches → calculate similarity → wait`. Absolutely not.

## The strategic reason M3 matters

This is the first moment where your project stops being **"Here are my five football studies"** and becomes **"Here's a football research system you can actually use."**

**M3 should not try to make the tool look impressive by adding features.** The killer experience is simply:

> **Search player → choose league → find similar players → understand why → see where similarity breaks.**

> **Similarity asks: "Who looks like him?"**  
> **Transferability asks: "What happens if he moves?"**
