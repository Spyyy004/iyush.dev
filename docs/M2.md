### Goal

Turn the five studies from "pages on a website" into a **coherent research product**.

> **Question → Context → Method → Evidence → Finding → Implication → Next study**

And importantly, the five studies should feel like **one investigation**, not five blog posts.

# 6. The "Why This Study?" Section

This should be short.

Example:

### Why this matters

Raw statistics make player comparison deceptively simple.

A player producing 0.70 xG+xA/90 against weak opposition isn't necessarily equivalent to a player producing 0.55 against strong opposition.

So:

> **Can we separate player level from opponent difficulty?**

That's the question.

---

# 7. Method Section

Don't dump methodology immediately.

Use a compact visual:

```text
PLAYER OUTPUT
      +
TEAM / SEASON CONTEXT
      +
VENUE
      +
OPPONENT STRENGTH
      ↓
ADJUSTED PLAYER OUTPUT
```

Then:

### Technical detail

Expandable.

For example:

> Player-level estimates use within-player PPML models with player × team × season fixed effects and clustered errors.

Then:

**Why this matters →**

> We're comparing a player's output against different contexts rather than simply comparing raw totals.

The technical audience gets the real methodology.

The normal football fan doesn't get punished for not knowing PPML.

# 8. The Main Finding

Every study needs **one enormous finding.**

For Study 3:

# **A stronger opponent hurts everyone.**

Then:

```text
+1 SD opponent strength

xG             −13.8%
xA             −15.1%
Shots          −10.5%
Key passes     −11.4%
Goals          −15.8%
```

This should be the visual centrepiece.

Underneath:

> Moving from a typical opponent to one standard deviation stronger is associated with roughly 14% lower xG per 90, after accounting for player, team, season and venue context.

Then glossary links for:

`SD`, `xG`, `xA`.

---

# 9. "How Big Is That?" Visualization

Every major finding should answer:

> Is that actually a lot?

For example:

```text
WEAKEST FIFTH ───────────────── STRONGEST FIFTH

xG
████████████████████████
                    █████████████████
                         −33%
```

For Study 3:

> The difference between the weakest and strongest opponent groups is roughly **−33% xG**.

This is much more intuitive than simply showing `−13.8%`.

---

# 10. The Individual Player Question

This is where the research becomes interesting.

After showing the aggregate effect:

# **But are some players different?**

Then:

> Maybe the average effect is strong, but certain players are unusually resistant to elite opposition.

Then show:

```text
PLAYER × METRIC ESTIMATES

23,022 tested

RELIABLE RESISTANCE

0
```

Large.

Then:

> We found no reliable individual player × metric estimates showing consistent resistance to stronger opposition.

This is a perfect example of the site's philosophy:

**The interesting result isn't always a positive result.**

---

# 11. The "We Were Wrong" Pattern

I want every study to explicitly expose what the analysis challenged.

Example Study 3:

### What the raw data suggested

> Some players appeared to perform disproportionately well against elite opposition.

### What happened after adjustment

> The apparent pattern disappeared.

### Lesson

> Raw "big-game" records can reflect context and noise rather than a stable player trait.

This should become one of the defining characteristics of the site.

---

       ↓

# 22. The Model's Failure

This should **absolutely** be visible.

# **Where the model breaks**

Example:

> The model under-predicts low-output central midfielders moving into the Premier League.

Then:

**Example: Ugarte**

```text
Predicted     0.02
Actual        0.14
```

And:

> The model primarily sees attacking output. It cannot see defensive work.

This is excellent product design.

Most portfolio projects hide model failures.

We should make ours part of the story.

This is the one study we **must not pretend is finished**.

The research document explicitly says the five-league weather confirmation/final freeze remains pending.

Therefore the Study 1 page should visibly distinguish:

> Effects mostly within ±2–2.5%.

### Open

> Still under investigation.

This means Study 1 should probably have two internal sections:


**Do not let the UI imply Study 1 is fully frozen.**

# 29. M2 Mobile

Research pages must be excellent on mobile because **this is likely where Reddit/social traffic lands.**

Mobile order:

```text
Study number
↓
Question
↓
Finding
↓
Evidence
↓
Explanation
↓
Method
↓
Player result
↓
Limitations
↓
Next study
```

Charts:

- no tiny labels
- horizontally scroll only where unavoidable
- key result stated as text above chart

Example:

> **xG falls 13.8% for every +1 SD increase in opponent strength.**

Then chart.

Never force the user to read the chart to understand the conclusion.

# 33. M2 Data Contract

I'd define study content roughly like:

```typescript
type Study = {
  id: number
  slug: string
  title: string
  question: string
  status: "final" | "pending" | "live"
  period: string
  leagues: string[]
  sample: {
    matches?: number
    playerMatches?: number
    players?: number
  }

  summary: string

  sections: {
    whyItMatters: string
    method: string
    findings: Finding[]
    limitations: string[]
  }

  nextStudy?: string
}
```

And:

```typescript
type Finding = {
  title: string
  value?: string
  metric?: string
  explanation: string
  chart?: ChartData
}
```

The research content should be **data-driven**, not hardcoded into React components.

# 34. M2 Acceptance Criteria

We stop M2 only when:

### Research architecture

- [ ] `/research` exists
- [ ] Five studies have dedicated routes
- [ ] Studies feel like one investigation
- [ ] Previous/next navigation works
- [ ] Study status is visible

### Research UX

- [ ] Every study begins with a question
- [ ] Finding appears before technical detail
- [ ] Methodology is progressively disclosed
- [ ] Major results have visual evidence
- [ ] Limitations are visible
- [ ] "What surprised us" / interpretation exists
- [ ] Next question links studies together

### Scientific integrity

- [ ] No research values invented
- [ ] No claims beyond the final research document
- [ ] Study 1's pending weather freeze is explicitly represented
- [ ] Study 5's model limitations are visible
- [ ] Prediction ≠ certainty
- [ ] Similarity ≠ transfer prediction

### UX

- [ ] Glossary tooltips work
- [ ] Charts have textual interpretation
- [ ] Mobile layout works
- [ ] Accessibility maintained
- [ ] Loading/error/empty states exist where needed

### Performance

- [ ] Research pages don't load raw datasets
- [ ] Charts are lazy-loaded where appropriate
- [ ] Static research content loads quickly
